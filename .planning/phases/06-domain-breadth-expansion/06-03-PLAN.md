**Scope decision**: went with Task 1's recommended option (a) -- shipped

**Two real bugs found and fixed while building this, both affecting existing production
code, not just this new server:**

1. **`httpx2.AsyncClient` wrapping a raw `httpcore2.AsyncConnectionPool` transport is
   broken** in the exact versions this project locks (httpx2==2.13.1, httpcore2==2.13.1,
   confirmed identical in `mcp/nwdaf/uv.lock`) -- `httpcore2`'s connection pool calls
   `request.url.scheme.decode()` on a value httpx2 already passes as a `str`, raising
   `AttributeError` on every single request. **This is NWDAF's own `_create_client()`
   h2c branch, unchanged since it was written** -- meaning `get_nwdaf_analytics` likely
   fails the same way against the live NextGCore backend today. Fixed in `mcp/udr/server.py`
   with a small `_H2CClient`/`_H2CResponse` wrapper that drives `httpcore2`'s pool directly
   (byte-level `.request()`, matching the pattern that got real responses during this
   session's live investigation), bypassing httpx2's broken translation layer entirely.
   **Not backported to NWDAF** -- out of scope for this plan, flagging for a follow-up.
2. **`h2` (the actual HTTP/2 protocol implementation `httpcore2` needs for its HTTP/2
   support) was never declared as a dependency anywhere** -- not in `mcp/nwdaf/pyproject.toml`,
   not resolved transitively in its lockfile. Any real h2c connection attempt would hit
   `ModuleNotFoundError: No module named 'h2'` before even reaching bug #1. Added
   `h2>=4.1.0` to `mcp/udr/pyproject.toml` explicitly; NWDAF's `pyproject.toml` still
   doesn't have it.
3. **Path base mismatch**: `UDR_BASE_URL` was initially set to `http://udr.otel25-backends.svc.cluster.local:7777`
   (host:port only). NextGCore's UDR requires the full `/nudr-dr/v2` spec base path --
   same "NextGCore uses the full path, Prism strips it" divergence NWDAF's own server.py
   comments already describe for `/nnwdaf-analyticsinfo/v1`. Fixed by setting
   `UDR_BASE_URL=http://udr.otel25-backends.svc.cluster.local:7777/nudr-dr/v2` in the
   `backend-routing` ConfigMap (`otel25-mcp` namespace).

**Combined, bugs #1 and #2 mean NWDAF's h2c path has very likely never worked against the
live NextGCore backend** -- consistent with `NWDAF_PROTOCOL` being entirely absent from
the `backend-routing` ConfigMap (silently defaulting to `"http1.1"`, which also wouldn't
work against NextGCore's h2c-only endpoint, just fails differently). Worth a dedicated
follow-up to confirm and fix NWDAF directly, not assumed from this alone.

**Spec sourcing**: pulled the authentication-subscription operation and its schemas from

## Why this, and why now

06-01's live probing confirmed UDR (Nudr -- generic 3GPP data-repository access) is the one 3GPP
core expansion candidate that actually works end to end: real `200` responses with genuine
3GPP-structured authentication-subscription data, against a test subscriber provisioned via
`nextgcore-webui` (found running in the existing `nextgcore-runtime` image, not previously deployed).
AMF, SMF, and UDM were all evaluated and ruled out for three distinct, documented reasons (see
06-01-PLAN.md's status updates). UDR is a genuinely new, confirmed-viable 3GPP core domain --
the first since NWDAF.

## What's already confirmed (don't re-probe)

- UDR binds `0.0.0.0:7777` correctly, reachable via its Service from other pods
- Needs the same h2c-prior-knowledge transport as NWDAF (raw `httpcore.AsyncConnectionPool(http1=False, http2=True)`, NOT `httpx.AsyncClient` wrapping a raw httpcore transport directly -- that combination hits a real `request.url.scheme.decode()` AttributeError in the httpx/httpcore versions available, confirmed live twice this session)
- `GET /nudr-dr/v2/subscription-data/{supi}/authentication-data/authentication-subscription` returns real structured data for a provisioned subscriber (`authenticationMethod`, `encPermanentKey`, `encOpcKey`, `authenticationManagementField`, `sequenceNumber`)
- `GET /nudr-dr/v2/subscription-data/{supi}/provisioned-data/am-data` returns `200` but empty `{}` with the webui's minimal provisioning payload -- the webui's `POST /api/subscribers` only populates security data, not AM-subscription-data/slice info
- A test subscriber already exists: `imsi-999700000000001` (provisioned via `nextgcore-webui`, see 06-01 for the exact payload shape)
