# Phase 6 Plan 2: CAMARA Device Status MCP Server

## STATUS UPDATE (2026-10-12): Built, deployed, and verified -- new `mcp/camara-device-status/` server, 3 tools

**Backend decision**: confirmed no live backend exists for CAMARA Device Status in this project
(checked `backends/prism/` and `backends/openshift/` -- only `prism-camara.yaml` and
`prism-camara-retrieval.yaml` existed, both Prism). Followed the same Prism-mock pattern as the
existing CAMARA Device Location server. Checked the Phase 4 Lorem-Ipsum concern proactively
before building: all three vendored r2.2 specs already ship multiple realistic named `examples`
per response (e.g. roaming status broken out by country code, reachability by connectivity type,
connected network type by generation) -- no enrichment was needed, confirmed after deploying by
querying each live Prism instance directly (responses matched the vendored examples verbatim,
no Faker/Lorem-Ipsum values).

**Spec sourcing**: pulled `device-roaming-status.yaml`, `device-reachability-status.yaml`, and
`connected-network-type.yaml` from `camaraproject/DeviceStatus` at release tag `r2.2` (confirmed
latest stable, non-prerelease). r2.2 also ships matching `-subscriptions` webhook/notification
variants for all three APIs -- left unvendored, since those are event-subscription shapes, not
request/response tool-calling shapes (same reasoning CAMARA Device Location's own API surface
never wrapped subscription-style operations).

**Server structure decision**: built a new `mcp/camara-device-status/` directory rather than
extending `mcp/camara/server.py`. Device Status is a different upstream repo entirely
(camaraproject/DeviceStatus vs. camaraproject/DeviceLocation) with 3 independent single-operation
specs, each needing its own Prism instance and ConfigMap-routed backend URL. Adding all 3 to the
existing camara/server.py would have pushed it to 5 ConfigMap watchers and 5 httpx2 clients in one
file; a separate directory keeps each domain server focused, matching how NWDAF and the TMF
servers already get their own directories rather than being grouped by source organization.

**Built**: 3 explicit `@mcp.tool()` functions (`get_roaming_status`, `get_reachability_status`,
`get_connected_network_type`), one per spec, each POSTing to its own Prism-backed `/retrieve`
endpoint via a dedicated ConfigMap-watched `httpx2.AsyncClient`. New backend-routing ConfigMap
keys: `CAMARA_ROAMING_BASE_URL`, `CAMARA_REACHABILITY_BASE_URL`, `CAMARA_NETWORK_TYPE_BASE_URL`.
Three new Prism Deployments/Services in `otel25-backends`
(`prism-camara-roaming`/`-reachability`/`-network-type`) built from the existing parameterized
`backends/prism/Dockerfile` pattern, and one new MCP server Deployment/Service in `otel25-mcp`
(`mcp-camara-device-status`), all built and pushed to the in-cluster registry and deployed via
`oc apply`.

**Verified**: all 3 Prism mocks return realistic 200s directly (curl), and all 3 tools verified
end-to-end over the real MCP protocol (`fastmcp.Client` `list_tools` + `call_tool` against the
port-forwarded `mcp-camara-device-status` service) -- each returns valid, schema-correct JSON
matching the vendored spec's named examples. Pods stable with no restarts after deploy.

**Not done (explicitly deferred per this plan's scope)**: gateway registration
(`MCPServerRegistration`) and `seed-scenarios.yaml` curriculum additions -- bundled into 06-03
alongside the UDR server per the batching decision in 06-01.

## Why this, after 06-01

06-01 closed out the 3GPP core expansion avenue for now: AMF is blocked by an upstream NextGCore
bug, and SMF -- though reachable and spec-real -- turned out to be NAS-signaling passthrough,
not a fit for agentic tool-calling. CAMARA Device Status is the next-best candidate from the
original scoping research: plain JSON REST (same shape as the existing CAMARA location API
already in this project), confirmed stable release maturity, and the only one of the 7
candidate CAMARA APIs with real thematic adjacency to fault-prediction/NOC work (device
connectivity/roaming state, not subscriber identity or billing).

## Tasks

Unlike NWDAF/AMF/SMF (NextGCore, a live reference core), CAMARA Device Status needs its own
backend decision -- check whether a live backend exists anywhere in this project's reach, or
whether this follows the existing CAMARA location pattern (Prism mock, enriched with realistic
example values, since generic Prism output was confirmed unusably generic in Phase 4).

### Task 2: Source the CAMARA Device Status OpenAPI spec

Pull the current stable release from `camaraproject/DeviceStatus` on GitHub (confirmed r2.2 as
of the 06-01 scoping research). Follow the same spec-sourcing/attribution pattern already used
for `mcp/camara/specs/camara_location_retrieval.yaml`.

### Task 3: Build `mcp/camara/` additions (or a new `mcp/camara-device-status/` -- decide based on
whether the existing `mcp/camara/server.py` multi-spec pattern fits, since CAMARA already
handles more than one spec file for location retrieve/verify)

Mirror the existing CAMARA server pattern:
- Spec file under `mcp/camara/specs/`
- Curated `@mcp.tool()` additions to `mcp/camara/server.py` (or a new server if the multi-spec
  pattern doesn't fit cleanly)
- Allowlist entry matching the existing `allowlist_verify.yaml`/`allowlist_retrieve.yaml` pattern
- If backed by Prism: enrich the spec with realistic example values up front, don't wait to
  discover generic/unusable mock output the way Phase 4 did for TMF/NWDAF

### Task 4: Deploy and verify

Verify each curated tool individually against its backend (live or Prism), same bar as every
other domain server in this project.
