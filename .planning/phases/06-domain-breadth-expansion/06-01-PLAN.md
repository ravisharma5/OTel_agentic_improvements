# Phase 6 Plan 1: AMF Live Probe and MCP Server

## STATUS UPDATE (2026-10-12): AMF probe complete -- not viable, pivoting to SMF first

Live probe confirmed AMF's SBI port (7777) is bound to `127.0.0.1` inside its pod, not
`0.0.0.0` -- unreachable via its own Kubernetes Service from any other pod, despite the
mounted `amf.yaml` config already declaring `sbi.server[0].address: 0.0.0.0`. Comparison
against SMF (same `NEXTGCORE_SBI_PROFILE: dev` env var, same binary family) confirmed SMF
correctly binds `0.0.0.0:7777` and is reachable -- isolating this to a NextGCore AMF-daemon
(`nextgcore-amfd`) dev-profile bug that overrides its own YAML config, not a deployment
misconfiguration on our side. This was already a known, documented constraint from Phase 1
(see the readiness-probe comment in `backends/openshift/nextgcore/deployment-nextgcore.yaml`:
"AMF binds SBI to 127.0.0.1 in dev mode") -- it just hadn't mattered until now, since nothing
needed to call AMF's SBI from outside its own pod before.

**Decision**: AMF is blocked on an upstream NextGCore limitation, not something fixable from
our deployment manifests. Pivoting Task 2/3 below to SMF first (confirmed reachable). AMF
stays flagged as blocked -- revisit only if a NextGCore version/build without this bug shows
up, or if patching NextGCore's own source becomes in scope.

## STATUS UPDATE (2026-10-12): SMF probed -- reachable and real, but a poor domain fit

Live probe (raw HTTP/2 prior-knowledge, working around an unrelated `httpx2`/`httpcore2`
v2.13.1 bug -- `request.url.scheme.decode()` called on a `str`) confirmed SMF's SBI is a real,
spec-compliant `Nsmf_PDUSession` implementation, not a stub: `POST /nsmf-pdusession/v1/sm-contexts`
progressed through two distinct real validation stages (generic "mandatory IE missing" ->
specific "n1SmMsg binary part missing or invalid"), and GET-based list endpoints correctly
404 (Nsmf_PDUSession's spec never defines list endpoints -- expected, not a gap).

**The actual problem: Nsmf_PDUSession's entire operation set is NAS-signaling passthrough,
not a query/observability API.** Every meaningful operation (create/retrieve/modify/release
SM context) requires a `multipart/related` body containing a binary-encoded NAS PDU Session
Establishment Request as the `n1SmMsg` part. This is deep core-network signaling -- nothing
a NOC fault-prediction agent would naturally construct as a diagnostic tool call, unlike
NWDAF's plain-JSON `GetNWDAFAnalytics` or TMF's REST CRUD. Building a tool around it would
mean fabricating a synthetic NAS binary blob with no real semantic content for the agent to
reason about -- exactly the non-representative-data problem this project's tool-coverage
gate exists to catch, not something worth generating on purpose.

**Decision**: do not build an SMF MCP server. This is a different category of finding than
AMF -- SMF isn't blocked by infrastructure, it's a poor fit for agentic tool-calling by the
nature of its own API shape. Worth generalizing: NWDAF fits this project's tool-calling model
because it's explicitly an analytics/observability function by 3GPP design. Most other 3GPP
core SBI interfaces (session/mobility management, like AMF's Namf_Communication and SMF's
Nsmf_PDUSession) are signaling-oriented, not query-oriented, and may share this same
poor-fit problem -- not confirmed for UDM/UDR/AUSF specifically, but the pattern is a reason
to probe-before-building there too rather than assume they're more NWDAF-like than SMF was.

**Pivoting Phase 6's remaining scope to CAMARA Device Status** -- plain JSON REST, confirmed
stable maturity, a natural tool-calling fit. See 06-02-PLAN.md.

## STATUS UPDATE (2026-10-12): UDM/UDR probed -- UDR confirmed viable, UDM blocked by a systemic NextGCore bug

Before fully abandoning 3GPP core, probed UDM (Nudm_SDM) and UDR (Nudr) -- both are data-management
functions by 3GPP role, not signaling functions like AMF/SMF, so worth checking rather than assuming
they'd share the same poor fit. External research (separate parallel task) independently confirmed
this distinction matters: 3GPP TS 29.502 defines SMF's NAS-passthrough as a spec-level requirement for
*any* compliant implementation, not a NextGCore quirk -- switching 5G cores would never fix SMF. AMF's
loopback-bind bug looks more NextGCore-specific (Free5GC explicitly separates bind/register IPs for
exactly this Kubernetes scenario; Open5GS is fully configurable) -- but even a reachable AMF might
still be signaling-shaped like SMF, unconfirmed. One externally-published 2026 survey on agentic 5G/6G
networks independently names NWDAF specifically as the natural MCP integration point, not AMF/SMF --
unprompted corroboration of this project's own hands-on finding.

**UDM and UDR both bind correctly (`0.0.0.0`) and both returned real, structured, spec-compliant
responses when probed** (UDM: a genuine 503 "UDR unavailable" proving the endpoint is implemented and
actively tries to proxy to UDR; UDR: clean 404 "Subscriber not found" for a fabricated IMSI, proving
real lookup logic) -- a categorically different and better signal than SMF's signaling-passthrough
shape. The only gap was no subscriber data seeded anywhere (`mongosh` showed no NextGCore database at
all).

**Provisioning solved**: found `nextgcore-webui`, a Rust binary present in the already-built
`nextgcore-runtime` image but not deployed anywhere -- a bearer-token-authed REST API + dashboard for
subscriber management (refuses plaintext HTTP by default, needs `--insecure-dev` for non-TLS; a
genuinely good security default). Ran it as a throwaway pod against the existing MongoDB, provisioned
one test subscriber (`imsi-999700000000001`) via `POST /api/subscribers`, cleaned up after.

**UDR: confirmed working end to end.** `GET /nudr-dr/v2/subscription-data/{supi}/authentication-data/authentication-subscription`
returned a genuine `200` with real 3GPP-structured data (`authenticationMethod`, `encPermanentKey`,
`encOpcKey`, `authenticationManagementField`, `sequenceNumber`). **This is a confirmed-good MCP
tool-calling candidate today.**

**UDM: blocked by a different, more systemic bug than AMF's.** Root-caused via NRF's own stored
instance records: every NF registers itself with NRF using `0.0.0.0` as its own advertised address --
literally the bind wildcard, not a routable IP (confirmed on both UDM's and SMF's NRF instance
records). So when UDM does NRF-based service discovery to find UDR, it gets back `0.0.0.0:7777`,
meaningless as a connection target from another pod -- this is why UDM's proxy-to-UDR call 503s
regardless of UDR's own health. Tried patching `udm.yaml` with a static `client.udr.uri` override
(mirroring the existing static `client.nrf.uri` pattern already in use) -- no effect; UDM's binary
doesn't appear to honor a static UDR override, it's hardcoded to NRF-based discovery. Reverted the
ConfigMap and restarted UDM back to its original state; no lingering cluster changes. Also found, as a
side discovery: NRF's `nf-type` query filter is broken (querying `nf-type=UDR` also returns UDM/SMF
instances) -- a second, independent NRF bug, not pursued further since UDM's blocker doesn't depend on
fixing it.

**This NRF self-registration bug (`0.0.0.0` as advertised address) is a systemic issue, not
UDM-specific** -- it would block *any* NF-to-NF call that goes through NRF-based discovery, which is
most inter-NF communication in a real 5G core. Worth flagging for PCF too, if that's ever deployed
(PCF's binary is confirmed present and deployable via the same pattern as the other 8 NFs, but its
own policy-decision operations likely need to discover subscriber/session data from other NFs the
same way UDM does -- probably hits the identical bug, not tested).

**Decision**: build the UDR MCP server (confirmed real data flowing for authentication-subscription
data at minimum; AM-subscription-data returned `200` but empty `{}` with the webui's minimal
provisioning payload -- richer provisioning could fill this in later, not blocking a first server).
Skip UDM entirely -- blocked on an upstream bug with no viable workaround found. Do not pursue PCF
without first confirming it doesn't hit the same NRF self-registration bug.

**3GPP core expansion final tally for this phase**: NWDAF (existing) + UDR (new) are viable.
AMF, SMF, UDM are not, for three different and now well-documented reasons (loopback bind bug,
spec-level NAS passthrough, NRF self-registration bug). See 06-03-PLAN.md for the UDR server build.


## Goal

Confirm NextGCore's AMF (Namf_Communication) exposes a real, queryable API surface -- not just the bare NRF-registration path it needs to satisfy NWDAF's dependency chain -- then build the AMF MCP server following the existing NWDAF/CAMARA pattern if viable.

## Why this order

The scoping research (fork, 2026-10-11) found AMF/SMF/UDM/UDR/AUSF deployed in NextGCore's `dev` profile specifically to satisfy NWDAF's registration handshake, not confirmed as feature-complete SBI implementations. Before investing in spec-bundling, tool design, and gateway registration, confirm the live service actually answers real `Namf_Communication` queries (e.g. `UEContextStatus`, connection status lookups), not just NRF registration. This is the same shape of surprise already hit once with NWDAF's h2c transport mismatch -- probe first, build second.

## Tasks

### Task 1: Live probe against the running AMF service

- Confirm AMF is reachable at `amf.otel25-backends.svc.cluster.local:7777` (or current equivalent) from a pod in the same cluster/namespace as the other MCP servers.
- Attempt a real `Namf_Communication` operation (e.g. `UEContextStatus` or a UE connection list query) against it, not just a health/registration check.
- Determine transport: confirm whether AMF's SBI serves HTTP/2 cleartext (h2c) like NWDAF did, requiring the same client workaround already built for NWDAF.
- **Decision point**: if AMF answers real queries, proceed to Task 2. If it only responds to NRF-registration-shaped traffic, stop and report back -- this would mean AMF isn't viable without additional NextGCore configuration work, a different scope than originally planned.

### Task 2: Build the AMF MCP server (if Task 1 confirms viability)

Mirror the NWDAF pattern exactly:
- Source the official `Namf_Communication` OpenAPI spec (3GPP TS 29.518, 3GPP Forge) and bundle its `$ref`s the same way `nwdaf_analyticsinfo_bundled.yaml` did, for Prism mock compatibility -> `mcp/amf/specs/amf_communication_bundled.yaml`
- Run `openapi-to-mcp` to scaffold, then hand-curate to explicit `@mcp.tool()` decorators (multi-spec domain pattern, same reason NWDAF/CAMARA did this instead of using the generated scaffold directly -- avoids tool-name double-prefixing)
- `mcp/amf/allowlist_communication.yaml` (documentation-only, matching the camara/nwdaf allowlist pattern)
- `mcp/amf/server.py` with ConfigMap file-watcher for `AMF_BASE_URL`, same h2c-vs-HTTP/1.1 transport selection logic as NWDAF if Task 1 confirms AMF also needs it
- `mcp/amf/Dockerfile`, `pyproject.toml`, `uv.lock` matching nwdaf/camara structure

### Task 3: Deploy and verify

- Build and deploy the AMF server container
- Verify each curated tool individually returns a valid, schema-conforming response from the live AMF service
- Do NOT register behind the gateway yet -- that's bundled into 06-03 alongside SMF and CAMARA Device Status, so the gateway config gets updated once per batch instead of three times

## Success Criteria

1. AMF's real API surface is confirmed (or confirmed not viable, with evidence, if that's the outcome)
2. If viable: AMF MCP server exists, deployed, and each tool verified individually against the live service
3. Findings documented (viable or not) before Phase 6 Plan 2 (SMF) starts, since SMF likely shares the same dev-profile-depth risk
