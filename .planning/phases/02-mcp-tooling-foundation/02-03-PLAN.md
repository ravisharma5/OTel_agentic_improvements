<objective>
Build the reusable OpenAPI-to-MCP conversion CLI and validate it by generating a working FastMCP server from the CAMARA Device Location spec.

Purpose: Phase 3 needs this CLI to bootstrap 20 curated MCP tools from 5 different OpenAPI specs. The CLI generates server scaffolds with operation filtering (via YAML allowlist) and ConfigMap file-watching (for backend URL switching) baked in, so each domain server starts with BACK-03 compliance built-in rather than reimplementing it.
Output: Working conversion CLI at mcp/tooling/openapi_to_mcp.py, validated via CAMARA smoke test producing a server that starts and lists its tools.

**Pattern deviation:** This plan uses an inline Python string template (textwrap.dedent/str.format) in openapi_to_mcp.py instead of the separate Jinja2 file (mcp/tooling/templates/server_template.py.j2) listed in 02-PATTERNS.md's File Classification table. This avoids adding a Jinja2 dependency for a single template use. See 02-RESEARCH.md Pattern 2's "e.g., Jinja2 or string templates" alternative -- inline string template is the simpler option for one template with straightforward variable substitution.
</objective>

    Create mcp/tooling/openapi_to_mcp.py implementing the conversion CLI per D-11, D-12, D-13, D-16.

    CLI interface using argparse with arguments: --spec (required, path to OpenAPI spec YAML/JSON file), --allowlist (required, path to allowlist YAML config), --output (optional, path for generated server.py, default ./server.py).

    Main logic:
    1. Load the allowlist config using allowlist_schema.load_allowlist(args.allowlist)
    2. Verify the spec file exists at the path from --spec argument (not from the allowlist config -- the allowlist's spec_path field is for baking into the generated scaffold)
    3. Generate a standalone server.py scaffold as a Python string using textwrap.dedent and str.format (no external template engine -- deviates from 02-PATTERNS.md's server_template.py.j2 suggestion to avoid a Jinja2 dependency for a single template; see 02-RESEARCH.md's "string templates" alternative). The generated scaffold must contain ALL of the following sections:

    Section A -- Header: auto-generated comment with spec filename, allowlist filename, generation timestamp, and curation guide (edit descriptions in customize_components, adjust route_maps, or replace from_openapi with explicit @mcp.tool decorators; do NOT edit the ConfigMap watcher section).

    Section B -- Imports: os, json, threading, pathlib.Path, fastmcp.FastMCP, fastmcp.server.providers.openapi.RouteMap, fastmcp.server.providers.openapi.MCPType, fastmcp.server.providers.openapi.OpenAPITool, httpx.

    Section C -- ConfigMap file-watcher (per RESEARCH.md Pattern 3, with BACK-03 client.base_url fix): BACKEND_ROUTING_PATH env var defaulting to /config/backend-routing/{allowlist.backend_env_var}. _backend_url_lock as threading.Lock. _backend_url defaulting to http://localhost:4010. _load_backend_url() reads the file, validates URL starts with http:// or https:// (per T-02-04), updates _backend_url under lock, AND directly mutates client.base_url to the new URL value. httpx.AsyncClient.base_url is a mutable property (confirmed on httpx 0.28.x); the module-level client variable is resolved via Python's late-binding name lookup, so it is available by the time _load_backend_url() is called at startup (Section E) and by the watcher thread. This ensures ConfigMap changes actually propagate to the HTTP client that FastMCP tools use for backend calls, intended to close the BACK-03 compliance gap. However, whether FastMCP from_openapi() internals re-read client.base_url per-request (vs. freezing it at tool-construction time) is unverified -- see RESEARCH.md Open Question 1 and STATE.md. If Phase 3 validation reveals it does not propagate, the alternative is to recreate the FastMCP app instance on backend-URL change. get_backend_url() returns current URL under lock (retained for use in initial client construction). _start_config_watcher() spawns a daemon thread polling mtime every 5 seconds. Uses simple mtime comparison (NOT inotify, NOT watchdog) because Kubernetes ConfigMap volumes use atomic symlink swaps that break inotify watchers (per RESEARCH.md Pitfall 4).

    Section D -- OpenAPI server setup: SPEC_PATH as Path pointing to the vendored spec file (path baked from --spec argument, resolved relative to the generated file). route_maps list generated from allowlist.operations: each OperationFilter becomes RouteMap(path=op.path, methods=op.methods, mcp_type=MCPType.{op.mcp_type}), followed by a catch-all RouteMap(mcp_type=MCPType.EXCLUDE). customize_components(route, component) stub function with a pass body and a comment for Phase 3 curation. httpx.AsyncClient with base_url from get_backend_url(). FastMCP.from_openapi() call with openapi_spec, client, route_maps, and mcp_component_fn=customize_components.

    Section E -- Startup: _load_backend_url() call (this both sets _backend_url AND mutates client.base_url to the file's current value), _start_config_watcher() call, if __name__ == "__main__": mcp.run(transport="http", host="0.0.0.0", port=8000).

    4. Write the generated scaffold to the output path
    5. Print summary: spec name, number of operations included, number excluded (total - included), output path
