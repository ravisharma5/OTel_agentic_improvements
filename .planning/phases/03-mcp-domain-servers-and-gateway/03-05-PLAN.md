    **Step 1: Copy ConfigMap to otel25-mcp namespace.**
    The backend-routing ConfigMap is in otel25-backends but domain server pods in otel25-mcp need it volume-mounted. Kubernetes ConfigMap volumes only work within the same namespace.
    Run: oc get configmap backend-routing -n otel25-backends -o yaml | sed 's/namespace: otel25-backends/namespace: otel25-mcp/' | oc apply -f -
    Verify: oc get configmap backend-routing -n otel25-mcp

    **IMPORTANT — Dual-namespace ConfigMap concern (for STATE.md):**
    This creates a DISCONNECTED COPY of the backend-routing ConfigMap in otel25-mcp. The original in otel25-backends (used by MCP-Telecom indirectly and Prism mocks) and this copy are NOT automatically synced. The ConfigMap's own documented "SWITCHING CONTRACT" says operators patch otel25-backends/backend-routing to switch backends — but the 5 new domain servers read the otel25-mcp copy.

    Document this in STATE.md Blockers/Concerns: "To switch backends for ALL tools (MCP-Telecom + 5 domain servers), operators must patch BOTH otel25-backends/backend-routing AND otel25-mcp/backend-routing. Phase 4 (which will switch NWDAF to live NextGCore) must be aware of this dual-namespace requirement."

    Add a comment at the top of the copied ConfigMap noting this:
    oc annotate configmap backend-routing -n otel25-mcp otel25.redhat.com/sync-note="Disconnected copy from otel25-backends. To switch backends, patch BOTH otel25-backends/backend-routing AND this copy. See STATE.md." --overwrite

    **Step 2: Create 5 deployment YAMLs.**
    Each file follows the mcp/openshift/mcp-telecom-deployment.yaml pattern with these modifications:

    For EACH of the 5 servers (tmf642, tmf628, tmf621, nwdaf, camara):
    - Deployment metadata.name: mcp-<server>
    - Deployment metadata.namespace: otel25-mcp
    - Deployment metadata.labels: app: mcp-<server>, layer: mcp, domain: <domain> (tmf for TMF servers, nwdaf, camara)
    - Container name: mcp-<server>
    - Container image: image-registry.openshift-image-registry.svc:5000/otel25-mcp/mcp-<server>:latest
    - Container port: 8000
    - Resources: requests cpu 250m memory 256Mi, limits cpu 500m memory 512Mi
    - readinessProbe: httpGet /healthz port 8000, initialDelaySeconds 5, periodSeconds 10
    - livenessProbe: tcpSocket port 8000, initialDelaySeconds 10, periodSeconds 30
    - volumeMounts: name backend-routing, mountPath /config/backend-routing, readOnly true
    - volumes: name backend-routing, configMap name backend-routing
    - Service: ClusterIP on port 8000 targeting 8000

    The 5 deployment files are near-identical; only name, image ref, and domain label vary.
  </action>

    **Step 1: Generate lockfiles and finalize Dockerfiles for all 5 domain servers.**
    For EACH server (tmf642, tmf628, tmf621, nwdaf, camara):
    a) Initialize uv lockfile: cd mcp/<server> && uv lock
    b) Update the Dockerfile to use the lockfile for reproducible builds. Change:
       - The COPY line to include uv.lock: COPY pyproject.toml uv.lock ./
       - The RUN line to use --frozen: RUN uv sync --no-dev --frozen
       This is intentional two-phase Dockerfile finalization: Plans 03-02/03-03 scaffold Dockerfiles without lockfiles (since uv.lock does not exist yet), and this step finalizes them once uv lock has generated the lockfile. This aligns with 03-PATTERNS.md's canonical Dockerfile pattern (COPY pyproject.toml uv.lock ... + uv sync --no-dev --frozen).

    **Step 2: Build container images.**
    For EACH server (tmf642, tmf628, tmf621, nwdaf, camara):
    a) Build: podman build --platform=linux/amd64 -t mcp-<server>:latest -f Dockerfile .
       (Note: --platform=linux/amd64 required when building on ARM macOS for x86 OpenShift cluster, per 02-02-SUMMARY.md deviation #2)
    b) Tag for internal registry: podman tag mcp-<server>:latest image-registry.openshift-image-registry.svc:5000/otel25-mcp/mcp-<server>:latest

    **Step 3: Push images to OpenShift internal registry.**
    Login to registry if not already: oc registry login --skip-check
    For EACH server:
    podman push image-registry.openshift-image-registry.svc:5000/otel25-mcp/mcp-<server>:latest
    (If push fails due to registry routing, use: oc port-forward svc/image-registry 5000:5000 -n openshift-image-registry, then push to localhost:5000/otel25-mcp/mcp-<server>:latest)

    **Step 4: Deploy to OpenShift.**
    For EACH server:
    oc apply -f mcp/openshift/mcp-<server>-deployment.yaml
    Wait: oc rollout status deployment/mcp-<server> -n otel25-mcp --timeout=120s

    **Step 5: Verify all pods are Ready.**
    oc get pods -n otel25-mcp -l layer=mcp
    Expect: 6 pods (5 new domain servers + existing mcp-telecom), all 1/1 Ready.

    **Step 6: Run verification script for each domain.**
    For EACH domain (tmf642, tmf628, tmf621, nwdaf, camara):
    a) Port-forward: oc port-forward svc/mcp-<server> 8000:8000 -n otel25-mcp &
    b) Run: scripts/verify-domain-tools.sh <domain> http://localhost:8000
    c) Kill port-forward
    All 5 domains must pass (total: 20 tools verified).

    If any server fails readiness probes or tools/list returns wrong count, check logs: oc logs deployment/mcp-<server> -n otel25-mcp
  </action>
