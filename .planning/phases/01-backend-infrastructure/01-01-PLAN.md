<objective>
Create the foundational artifacts for Phase 1: vendor all 7 OpenAPI spec files into the repo, build a parameterized Prism Dockerfile, and create the three validation scripts that all subsequent plans depend on for verification.

Purpose: Every downstream plan (Prism deployment, NextGCore deployment, routing verification) depends on vendored specs and validation scripts existing first. This plan creates them with zero external dependencies.

The 7 spec downloads are mechanically identical operations (curl a pinned URL, validate the output format) with no hand-authored logic, so they do not warrant splitting into separate plans. The Dockerfile and scripts in Task 2 are tightly coupled to the spec files and form one coherent deliverable.

Note on bake-vs-mount (D-06 reconciliation): D-06 says "vendor specs into repo... mount into Prism container via ConfigMap." RESEARCH.md Pattern 1 (authored after D-06, during research) chose to bake specs into images via Dockerfile COPY instead. Both approaches satisfy D-06's core requirement: specs are vendored in the repo and not fetched from the network at deploy time. Baking is simpler for Phase 1 (no ConfigMap per spec, no mount path configuration). The Dockerfile COPY approach is used throughout this plan set per RESEARCH.md Pattern 1.
</objective>

    Create backends/prism/Dockerfile -- a parameterized Dockerfile that accepts SPEC_FILE as a build arg. Base image is stoplight/prism:5. The Dockerfile COPYs the spec file specified by SPEC_FILE into /specs/api.yaml inside the container. Set NODE_ENV=production (per RESEARCH.md anti-pattern: processing logs slow Prism without it). Use ENTRYPOINT ["node", "dist/index.js"] and CMD ["mock", "-h", "0.0.0.0", "-p", "4010", "--dynamic", "/specs/api.yaml"]. The -h 0.0.0.0 is mandatory (per D-08 and RESEARCH.md anti-pattern: Prism defaults to localhost which is unreachable from outside container). The --dynamic flag generates varied responses from schema (per D-08).

    Build context for this Dockerfile is the backends/ directory. Build command pattern: podman build --build-arg SPEC_FILE=specs/tmf642_alarm_v5.0.1.oas.yaml -f prism/Dockerfile -t prism-tmf642 backends/

    Note on bake-vs-mount: This Dockerfile bakes specs into images (COPY) rather than mounting via ConfigMap. This satisfies D-06's core intent (vendor into repo, no network fetch at deploy time) per RESEARCH.md Pattern 1. ConfigMap mounting is not needed because specs are static pinned files; image rebuilds are the appropriate mechanism when a spec version changes.

    Create backends/scripts/validate-mocks.sh -- per D-09 and RESEARCH.md "Schema Validation Strategy", use a standalone validation script (NOT Prism validation-proxy, which would be circular). The script performs three levels of validation per endpoint: (1) HTTP 2xx response, (2) valid JSON body, (3) presence of spec-specific required fields to prove the response actually matches the OpenAPI schema structure, not just parseability.

    The script curls each of the 5 Prism mock endpoints (4 TMF/CAMARA-verify + 1 CAMARA-retrieval) with Prefer: dynamic=true header. Endpoints array:
    - tmf642|$TMF642_URL|/alarm|GET
    - tmf628|$TMF628_URL|/measurementCollectionJob|GET
    - tmf621|$TMF621_URL|/troubleTicket|GET
    - camara-verify|$CAMARA_URL|/verify|POST
    - camara-retrieval|$CAMARA_RETRIEVAL_URL|/retrieve|POST

    Per-endpoint field validation (addresses review concern: validate-mocks too weak to prove schema conformance): After confirming HTTP 2xx and valid JSON, the script must also check that the response body contains at least one spec-required field. Read each vendored spec to identify the concrete field names, then hardcode assertions per endpoint. Expected patterns (verify against actual specs when authoring the script):
    - TMF642 /alarm: response is an array; elements should contain "id" field (TMF convention for managed entities)
    - TMF628 /measurementCollectionJob: response is an array; elements should contain "id" field
    - TMF621 /troubleTicket: response is an array; elements should contain "id" field
    - CAMARA /verify: response object should contain "verificationResult" field
    - CAMARA /retrieve: response object should contain "lastLocationTime" or "area" field

    If a field check fails, report it as a warning (not a hard failure) since Prism dynamic mode may omit optional fields. The HTTP 2xx + valid JSON checks remain the hard pass/fail gates, but field checks provide confidence the response matches the spec rather than being generic JSON.

    The script should accept base URLs via environment variables (TMF642_URL, TMF628_URL, TMF621_URL, CAMARA_URL, CAMARA_RETRIEVAL_URL) with defaults pointing to in-cluster Service DNS names (e.g., http://prism-tmf642.otel25-backends.svc.cluster.local:4010). Exit 0 on all pass, exit 1 on any failure.

    Create backends/scripts/verify-routing.sh -- per D-16, reads the backend-routing ConfigMap from OpenShift using oc, curls each URL from the ConfigMap, verifies 2xx responses. Then demonstrates the switching contract: patches one ConfigMap key (TMF642_BASE_URL) to a known-bad URL, re-reads, confirms it now points to the new value. Patches it back to the original value. Uses NAMESPACE variable defaulting to otel25-backends and CM_NAME defaulting to backend-routing. The key loop iterates over 6 keys: TMF642_BASE_URL, TMF628_BASE_URL, TMF621_BASE_URL, CAMARA_BASE_URL, CAMARA_RETRIEVAL_BASE_URL, NWDAF_BASE_URL.

    Create backends/scripts/check-nwdaf.sh -- per RESEARCH.md NWDAF validation patterns. Curls the NWDAF analytics endpoint at $NWDAF_BASE_URL/nnwdaf-analyticsinfo/v1/analytics?event-id=LOAD_LEVEL_INFORMATION. Checks for HTTP 2xx response and non-empty JSON body. NWDAF_BASE_URL defaults to http://nextgcore-nwdaf.otel25-backends.svc.cluster.local:8080. Uses one-shot analytics queries, not subscriptions (per RESEARCH.md Pitfall 2: subscriptions are memory-only, lost on restart).

    Strengthened analytics field assertions (addresses review concern: check-nwdaf too weak to prove analytics are meaningful): Beyond checking for HTTP 2xx and non-empty JSON, the script must also verify the response contains analytics-specific fields per the TS 29.520 spec. Read the vendored nwdaf_analyticsinfo_rel16.yaml spec to identify concrete response field names. Expected patterns: the AnalyticsInfo response should contain fields like "analyticId" or "nfLoadLevelInfos" or "analyticsData" (exact field names depend on the Rel-16 spec structure). Check for at least one analytics-identifying field using jq. Report field presence as a confidence indicator (warn if missing, since Prism dynamic mode may generate different structures for complex 3GPP schemas). The HTTP 2xx + non-empty JSON remain the hard pass/fail gates.

    All scripts use #!/usr/bin/env bash and set -euo pipefail. Make all scripts executable with chmod +x.
