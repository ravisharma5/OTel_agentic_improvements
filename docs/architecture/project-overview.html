Flow 1 — The end goal

Production Flow: a NOC engineer investigates a fault

This is what OTel 2.5 will do once trained — the six-step investigation sequence a human NOC engineer follows today, mapped to the telecom APIs OTel 2.5 will call to do it autonomously.

1

NOC Engineer / Operator

Notices or is alerted to a potential network fault. Asks — or an autonomous monitoring loop triggers — OTel 2.5 to investigate.

OTel 2.5 (the AI agent)

31B-param model, deeply trained on telecom standards. Decides which tools to call and in what order to diagnose the fault. This is the model this whole project exists to train — see Flow 2 below.

MCP Gateway

Phase 3

4

Tool servers — one per telecom domain

Each tile below is a step in the investigation. Click one to see exactly what it does.
TMF642 — Alarm MgmtPhase 3
Step: check active alarms
List, get, acknowledge, clear, and subscribe to network alarms. This is usually the first thing a NOC engineer checks — "what's currently raised, and how severe?"
TMF628 — Performance MgmtPhase 3
Step: pull KPI data
Pulls performance/KPI measurements for the network elements an alarm points at — is throughput down, latency up, errors spiking?
NWDAF — Predictive AnalyticsLive (backend)
Step: query 5G core predictions
Queries the 5G core's own built-in analytics (TS 29.520) — abnormal behavior, load level, congestion — the "is this about to get worse" signal. The live NextGCore backend for this is already running on OpenShift (Phase 1); the MCP tool wrapper around it is Phase 3.
CAMARA — Device LocationLive (backend)
Step: check affected devices
Checks whether affected devices/subscribers are connected and where — useful for scoping blast radius and ruling out device-side causes. Mock backends for this are already running on OpenShift (Phase 1).
MCP-Telecom — Device LayerPhase 2
Step: root-cause correlation
60+ existing tools (MIT-licensed, reused not rebuilt) for direct router/switch queries — interface status, CPU, memory, routing tables — correlating the alarm with what's actually happening on the physical/virtual infrastructure.
TMF621 — Trouble TicketPhase 3
Step: act on the diagnosis
Creates or updates a trouble ticket with everything gathered above as correlated evidence — alarms, KPIs, predictions, affected devices — the final step before handing off to resolution (or, for the closed-loop-automation use case down the roadmap, triggering automated remediation directly).
↓
5

Backends — something real for every tool call to hit

Every tool above needs a backend to actually respond. Phase 1 (shipped) deployed both kinds on OpenShift:
Prism mocksLive now
TMF642 / TMF628 / TMF621 / CAMARA ×2
Auto-generates schema-valid mock responses from each API's OpenAPI spec — used because TM Forum APIs have no public live backend to test against. 5 instances running on OpenShift today.
NextGCoreLive now
Real 5G core, not a mock
A genuine running 5G core (9 network functions — AMF, SMF, UPF, NRF, AUSF, UDM, UDR, MongoDB, NWDAF) with ONNX-backed analytics, deployed on OpenShift. NWDAF responses are real, not faked — this matters because fake analytics data would teach the model to expect nonsense.
Which backend answers each call is controlled by a ConfigMap — mock and live can be swapped per-API without touching any code, so the same tool definitions work whether the backend behind them is a Prism mock or a real system.

Flow 2 — What this project actually delivers

Training Flow: how OTel 2.5 gets built

OTel 2.5 doesn't exist yet as a deployed agent. This project's real deliverable is the training dataset and pipeline that teaches OTel 2.0 how to do everything in Flow 1 above.

Why this flow exists: OTel 2.0 already has deep telecom domain knowledge (31B params, ~440B telecom tokens of pretraining) but zero examples of actually calling telecom tools. This project builds that missing tool-calling training data — reusing the exact same MCP tools and backends shown in Flow 1.
1

Teacher model

Phase 4
A strong general-purpose LLM exercises the same MCP tools and backends from Flow 1 to generate candidate tool-calling conversations for the fault-prediction workflow.
↓
2

Execution verification

Phase 4
Every generated tool call actually runs against the real mock/live backend from Phase 1 — catching hallucinated parameters that a format-only check would miss. ~60-75% of parameter errors are caught this way.
↓
3

SDG pipeline (sdg_hub)

Phase 4
Orders examples by curriculum — single-tool → parallel → sequential → multi-turn → full closed-loop — and outputs both single-turn and multi-turn trajectory formats.
↓
4

Quality filter

Phase 4
8,500–14,000 raw generated examples filtered down to 5,000–10,000 high-quality, execution-verified training examples.
↓
5

Farbod's team (OpenTelco)

Not our scope
Runs OSFT — the actual fine-tuning — on OTel 2.0 using the delivered dataset. This project delivers data + pipeline only; training and evaluation belong to Farbod's team.

→

OTel 2.5

The fine-tuned model — which becomes the AI agent at the top of Flow 1. The loop closes.
